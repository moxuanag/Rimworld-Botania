## 1. 引擎与 API 陷阱（代码层，踩到就会「看起来没生效」）

| # | 现象 | 根因 | 正确做法 |
|---|---|---|---|
| 1 | 花一小时不动，然后一瞬间种十几株 | `CompProperties_ManaDevice.workIntervalTicks` 默认 **3600**（1 小时） | 显式写 `<workIntervalTicks>60</workIntervalTicks>` |
| 2 | 研究后实际半径变大，范围环还是小的 | `CompRadiusRing.Radius` 只读 Def 上的静态值，`MapComponent_Rings` 直接读 `Props.radius` | 加 `IDynamicRingRadius`（运行期环）与 `IDynamicPlaceRadius`（放置预览），由 Comp / CompProperties 实现 |
| 3 | 有草的格子永远不种 | `CanNowPlantAt(cell, map)` 默认把**任何植物**当阻挡 | 判定传 `canWipePlantsExceptTree: true`，并**自己** `Destroy` 那株植物（该开关只放行判定、不删植物） |
| 4 | 清完灌木，格子还是被占着，种不下 | `Plant.PlantCollected` 对 `harvestAfterGrowth > 0` 的植物是**回退成长度**，不是移除 | 想清空必须 `Destroy(DestroyMode.Vanish)`；要产出就先 `YieldNow()` 给产物再 Destroy |
| 5 | 神秘花描述写「采完还在、能再采」，实际采完就没了 | `PlantProperties.HarvestDestroys => harvestAfterGrowth <= 0`，神秘花没设该字段（=0） | 描述与机制必须对 Def 核实，不要沿用旧文案 |
| 6 | 两朵花重叠 → 原木翻倍 | 各自 `CountMatureTrees`，没有跨设备去重 | 「按环境数量给奖励」必须用 `MapComponent` 认领（本仓库 `MapComponent_TreeClaims`，按游戏日清空） |
| 7 | 英文描述改了但游戏里没变 | `Languages/English/DefInjected/` 里的 key 会**覆盖** `Defs/` 内联描述 | 描述只留一份；本次删掉 3 条过期覆盖键 |
| 8 | 同一个 defName 的中文描述有两份 | 同一 key 写进了两个 DefInjected 文件（后加载盖前加载） | 描述只写进「与 Def 同名的那一个」DefInjected 文件 |
| 9 | 界面出现 `Botania.Fertility.XXX` 原始字符串 | C# 用了 Keyed 但语言文件没补；**不报错**，直接显示 key | 加文案前先列全 key 清单，中英各补一条，占位符个数与 `Translate(...)` 实参一致 |
| 10 | 时间换算 | 1 天 = **60000** tick、1 小时 = **2500** tick、3 小时 = **7500** tick | 直接用 `GenDate.TicksPerDay` / `GenTicks`，不要手算魔法数 |

## 2. 设计与需求理解（这次最贵的部分）

### 2.1 用「局部优化」替代「按规则重写」

用户要的是：**编号 → 逐格短路判定 → 割除+种植 → 升级回扫 → 3 小时弱扫描**。
我先后做了：队列 + 游标 + 定时重建 + 廉价预筛 + 退避 + 事件驱动讨论……
每一步都在「优化扫描」，但没有一条是他要的规则。**代价：三轮返工、多次重写。**

教训：
- 当用户用「编号 / 一轮 / 回扫 / 每 N 小时」这种**流程语言**描述需求时，说明他要的是**状态机**，
  不是「更快的扫描」。先画状态机，再谈性能。
- 性能问题只有在「规则正确」之后才有意义；否则优化的是错的东西。

### 2.2 描述文案（已固化为 `AGENTS.md §1.1.1`）

踩过的具体错误：第二人称（「你替它选作物」）、相对数值（「赶得上熟练的园丁」）、
与风味段用词重复（太阳花「收进花心」）、语病（「那是她最早看懂的一件魔法」）、
把结果当描述写（「采完就没了」「要重新种」这类玩家一采就知道的东西）。
最终规则：花用**叙事体**（她 / 来历+动机 / 成长暗示），其它内容仍按 §1.1；
数值只进**检视面板**与**信息卡**；句子必须干净。

### 2.3 「圈」的语义没想清

魔力池黄圈画 6 格、真实网络半径 7 —— 两者长期不一致；而蓝色网络圈已经表达了覆盖范围。
**结论：网络类建筑（池 / 中继）不需要黄圈，黄圈只给「与网络无关的自身作用半径」。**

### 2.4 播种成本参与了「能不能动手」的判定

`cost = workPerPlant + 铲草成本`，而每秒累积只有 `workPerPlant` → **有草的轮次整轮放弃**，
玩家看到的是「铲完草停一秒才种」。铲草改为**零成本**、与播种合并成同一动作后消失。

### 2.5 定时重建导致「越种越慢」

播种队列每 300 tick 无条件重建、游标归零 → 已种过的格子要重新判定 → 最后几行最慢。
**教训：任何「从头重扫」的设计，在有累积状态的场景里都会变成 O(n²) 观感。**

### 2.6 视觉反馈与判定时机错位

绿框一开始放在「种下之后」，用户明确否定：**绿色应该表示「我判定这格能种、正在种」**，
从判定通过亮到种下为止；判定失败的格子另用琥珀短暂提示。

### 2.7 扣费顺序

先扣花瓣再付魔力 → 魔力见底那一瞬间白扣一片花瓣。正确顺序：
**查花瓣（只看不扣）→ 付魔力 → 扣花瓣**。

### 2.8 长期持有旧引用

判定时记下 `Plant` 引用、几秒后才去割——期间它可能已经被动物吃掉/枯萎。
**种植/割除前必须重新判定该格**（这正好也是规格 R6.5 的要求）。

## 3. 协作流程问题

| # | 问题 | 教训 |
|---|---|---|
| 1 | 任务书自身写错（三态门控写反、升级回扫时机与「研究完成立刻重编号」自相矛盾） | 子代理会**照错的做**。任务书里每个结论都要能对上规格文件的一句话 |
| 2 | 子代理用 PowerShell 批量替换把 UTF-8 写坏（中文变乱码） | 改文本一律用 `write` / `edit` 工具整文件写，不要 `-replace` + `Set-Content` |
| 3 | 半途叫停的子代理会留下半成品 | 叫停后必须 `git status` 检查 + `git checkout --` 回滚，再重新派单 |
| 4 | 我声称「已验证」，但只是编译通过 | 验收必须**逐条对规格**（本例 9 条检查项），不是只看 `check_all` |
| 5 | 用户反复说「你又听不懂」 | 需求复杂时，**先把理解写成文件给他确认**，再动手；不要靠对话里来回猜 |

## 4. 最终实现摘要（可复用）

### 4.1 状态机

```
编号(R1) → 主扫描(R3) ──走完──> 升级检查(R4) ──升级──> 回扫旧标记格+新增格 → 重编号 → 主扫描
                                   └──未升级──> 弱扫描(R5, 每 7500 tick)
弱扫描：比范围(R5.2) → 逐格收(R5.3) → 收完补种(R5.4) → 回扫不可种格(R5.5) → 等 3 小时
```

## 5. 下次做「复杂机制」的标准动作（checklist）

1. **先写规格文件**（现象 / 规则 / 状态机 / 数值 / 验收），放 `docs/`，提交；
2. 数值单独一张表，先让用户确认，再写代码；
3. 派单时把**规格文件路径**写进任务书，要求子代理先完整读、并声明「规格优先于任务书」；
4. 代码里每个分支标注规格编号（如 `R2.4`），便于逐条对照；
5. 子代理交付后，主代理**逐条对规格**验收（不是只看编译/check_all）；
6. 每次改完：`check_all` 7/7 → 部署 → 部署一致性 305/305 → `git status` 干净；
7. 用户实测反馈与预期不符时，**先定位是「规则没实现」还是「规则本身要改」**，
   不要在规则未定时做性能优化。
