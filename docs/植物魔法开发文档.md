# 第一部分 · 科技线与待实装内容

## 0. 文档沿革与已被推翻的结论

设计稿走过两版：`v0.4 提案`（科技线与装备体系）和 `v0.7 规划稿`（四个待实装研究）。
两版都有结论被实机推翻，这里集中记一次，后面不再重复：

| 原结论 | 实际情况 | 现在怎么做 |
|---|---|---|
| 精灵门做成「单个多格 Def + 检查邻接」 | `ThingDef.size` 是实心矩形，挖不出中间的洞 | 拆成上梁 + 左右柱三件 |
| 精灵门的转化做成 Bill 工作台 | 引擎没有干净的「Bill 扣魔力」接入点，自定义 JobDriver 实测不生效 | 改为投料自动转化（`CompManaGate`） |
| 魔力玻璃钢 = 魔力钢 + 玻璃 + 魔力 | 环世界没有玻璃这个物品 | 用**精灵石英**顶替玻璃 |
| 蓝图挂 `CompProperties_Techprint` 就「机制自然生效」 | 整条链路有三处皇权 DLC 硬门 | 自己补一条「解读蓝图」路径 |
| 盖亚之魂蓝图可以靠遗迹挖掘获得 | 已改为只由 Boss 掉落，遗迹挖掘作废 | Boss 未实装前不产出 |

## 1. 一句话概括

把 Botania 的「花 → 魔力 → 装备」改造成环世界的「研究 → 产能 → 装备」：
**时代推进靠研究点和工时，不靠堆材料层数；魔力作为电力的平行能源存在；装备每档只领先原版半个身位。**

---

## 2. 五条设计原则

| # | 原则 | 理由 |
|---|---|---|
| 1 | **两套能源不打架** | 魔力 ≠ 电力。通量场是唯一出口且打折（90%），让「扩花圃」和「扩电网」成为一笔要算的账，而不是免费电池 |
| 2 | **时代是门槛，材料不是门槛** | 能不能做取决于研究 + 设施（祭坛/灌注台/精灵门），不取决于凑齐七种材料。成品原料 ≤ 2 种 |
| 3 | **装备只领先半个身位** | 每档比同代原版强 10–20%，且**晚半代解锁**。环世界的平衡是「科技等级 vs 袭击强度」，超前装备会直接毁掉节奏 |
| 4 | **花是自动化，不是装饰** | 只保留能替代某个小人工作的花（种地/搬运/防御/发电）。纯装饰、纯方块交互一律砍 |
| 5 | **砍掉 MC 物理** | 方块、推动、红石、经验、附魔、飞行——环世界里没有对应物，硬做只会得到一堆不能用的东西 |

## 3. 五个时代

| 代号 | 时代 | 对应 techLevel | 研究点区间 | 这一代给玩家什么 | 对应 Botania 阶段 |
|---|---|---|---|---|---|
| E0 | 萌芽 | Neolithic/Medieval | 600–1200 | 花与花瓣的基本盘：采集、研磨、产地基材料 | 采集 → 花瓣 |
| E1 | 花圃 | Medieval | 1200–1800 | 第一批功能花：种地、搬运、防御 | 早期功能花 |
| E2 | 魔导 | Industrial | 1800–2600 | 魔力钢、法杖改型、魔力网络——开始「工业化」 | Manasteel 时代 |

## 5. 装备矩阵（v0.4 草案，未实装部分仍适用）

> 这一节是 v0.4 的装备草案；与后面 §9–§11 的定稿冲突时，**以 §9–§11 为准**。

**设计口径**：每档比同代原版高 10–20%，但解锁晚半步；不引入「耐久」（环世界没有这概念），质量走原版 quality 系统。

> **v0.4.1 的既成事实**：森林法杖已经是「主武器 + 魔力弹」——它就是我上一版想做的魔力枪。所以本节不再单列魔力枪，法杖本身占住 E2 的远程位。麻烦的是它现在挂在 900 点的 Medieval 研究下，见 §2 问题 2。

### 武器

| 时代 | 名称 | 类型 | 建议数值 | 对标 | 特殊机制 |
|---|---|---|---|---|---|
> **实装状态**：E1 基础法杖与 E2 两种改型都已在 0.6.0 实装，下表数值即代码真值。
> 早期草案里的「穿透型 / 散射型」在这一版定名为**狙击型 / 爆破型**，数值重排过一次。

| E1 | 森林法杖 | 远程 | 25 伤害 / 穿透 1.5 / 射程 26 / 预热 0.6 + 冷却 1.0s / 精度四档 80 | 狙击枪子弹 | 吃魔力不烧弹药；杖内 500、**每发 100**（满杖 5 发）；另带绽花 / 就地转化 |
| E2 | 法杖·狙击型 | 远程 | 50 伤害 / 穿透 2.4 / 射程 40 / 预热 1.0 + 冷却 1.5s / 精度四档 85 | 高穿狙击位 | 杖内 800、每发 60；**不带法术**（改造即失法） |
| E2 | 法杖·爆破型 | 远程 | 子弹 40 + 落点十字 10 / 射程 16 / 预热 1.2 + 冷却 3.0s / 精度 75·70·65·60 | 面杀伤位 | 十字＝中心 + 上下左右 5 格；**误伤友军与建筑**，打空也炸；杖内 700、每发 60；**不带法术**

> **爆破型的三条实现约束**（0.6.0 踩过，写下来免得重犯）：
> 1. **爆炸必须显式传 `overrideCells`**。`DamageWorker.ExplosionCellsToHit` 会做视线过滤，
>    并对每个空地补一圈相邻墙体（`openCells.Concat(adjWallCells)`），命中格数随地形浮动；
>    只给半径的话，「十字」在墙边会变成一大片。
> 2. **子弹本体不能复用 `Bomb` 伤害类型**。`Bomb` 对不可通行建筑有 4 倍倍率，
>    拿它做直击伤害会让面板上的 40 在墙上变成 160。原版子弹一律用 `Bullet`。
> 3. **爆炸伤害不要交给引擎结算**。即使传了 `overrideCells`，实测墙体仍稳定吃到
>    面板值的两倍（每格 80 而非 40），逐条核对反编译后没能定位到多出的那一倍。
>    现在由 `Projectile_WandBlast` 对 5 格里的每个 Thing 显式 `TakeDamage` 一次，
>    `GenExplosion` 只用来出表现（伤害传 0）。数字可预期比「引擎自己算」更重要。
>
> **另注**：面板伤害会吃品质加成（`RangedWeapon_DamageMultiplier` 带 `StatPart_Quality`，
> 大师 ×1.25、传奇 ×1.5），所以传奇狙击型是 75、爆破型子弹是 60。这是原版规则。

| E2 | 魔力钢剑 | 近战 | 伤害 22 / 穿透 25% / 冷却 2.0s | 略高于长剑 | 无（干净的过渡件） |
| E3 | 元素剑 | 近战 | 伤害 26 / 穿透 35% / 2.0s | 接近单分子剑 | 命中时有概率放出小精灵（小额额外伤害，纯演出向） |
| E3 | 水晶弓 | 远程 | 伤害 16 / 射程 30 / 2.2s | 高于大弓 | 同样吃魔力，不烧箭 |
| E3 | 泰拉刃 | 近战+ | 伤害 30 / 穿透 45% / 2.0s | 顶级近战 | 蓄力 8 秒可放一道 12 格魔力冲击（远程补刀） |

**关于基础法杖的取舍（已定案，走了第三条路）**

原草案是 A（把法杖挪到 E2）和 B（把数值砍到大弓档）二选一。实装时两条都没走，改成**压节奏**：

- **命中率四档统一 80**：这不是压制，是**加强**——近距从 45 提到 80，远距从 85 微降到 80。
  好处是它变成一把「手感稳定」的中距离武器，和原版狙击枪「远准近不准」区分开；
- **每发耗魔 50 → 100**：配合 500 储能，满杖只能打 **5 发**。基地里有池子照样无限打，
  出了魔力网立刻见底。

换句话说，**E1 确实有枪了，但那是一把能量受限的枪**：枪的强度靠魔力网兜底，
没网的时候它就是一根能打五下的木棍。这比 A（E1 没武器）更符合原版「有弹药才有枪」的节奏，
也比 B（砍伤害）更少改动既有手感。

> 遗留风险：如果后续实测发现 E1 仍然压过原版武器，**最小改动是把每发耗魔提到 150**（满杖 3 发），
> 不必动伤害与射程。这个旋钮留在 `CompProperties_ManaWeapon.manaPerShot` 一处。

**改型为什么砍掉法术**：绽花 / 就地转化在代码里是按「手里有 `CompWand`」授予的。
两个变体只挂 `CompManaWeapon`（它们要蓄能、要开火），不挂 `CompWand`，
所以改造的那一刻法术就从技能栏消失。这是有意为之——**改造是取舍，不是升级**：
拿 50 伤害和 30 射程，就得放弃对植物的支配。

### 引擎约束（设计时就必须算进去）

v0.4.1 踩到的硬规则：**这版引擎不会把「装备侧 Comp」的 gizmo 显示到小人身上**（原版只有服装侧的 `CompApparelReloadable` 是例外）。由此推出三条：

- 任何「穿上之后能操作」的能力（施法、充能、转化、开关）**必须做成 Verb**，走「征召 → 点按钮 → 选目标格」这条路；
- 装备自身的状态显示走 **Hediff**（v0.4.1 就是把「魔力储备 320/500」塞进健康面板的）；
- 范围提示走 **Comp / MapComponent 自绘**，不要指望 gizmo 或 tooltip。

这条约束会反过来影响所有装备设计：**不要规划「装备上挂一堆按钮」的交互**——那是 MC 的思路，环世界这边走不通。

**Harmony 的口子（0.6.0 起启用）**：这版引擎可以挂 Harmony，但只在一个地方用了它 ——
电暴花要监听 `ShortCircuitUtility` 的短路事件，而引擎没有给事件回调，只能打补丁。
原则仍然是「能用 Def + Comp 解决的，就不要打补丁」：

- 只补**数据拿不到**的地方（短路瞬间的电网储能），不补数值、不改原版 Def；
- 补丁方法体全部 try/catch，出错只记警告，绝不让原版逻辑中断；
- 补丁类是 `PatchAll()` 反射扫出来的，代码里没有引用，**不要当死代码删**；
- 依赖在 `About.xml` 的 `modDependencies` 里显式声明，缺了要让玩家在模组列表就看到。

## 6. 魔力经济

```
产：火红莲(燃料 30/s) · 地热火莲(间歇泉 60/s) · 食物花(1 餐 = 2000) · 水力花(待验证)
储：魔力池 10 万（现有）→ 扩容 25 万
输：中继塔（每跳 -10%，现有）
耗：通量场(1000W) · 灌注台 · 武器 · 精灵门
```

**红线**：魔力**不能**直接当电用。通量场是唯一出口且效率 90%；**不做「电 → 魔力」的反向**（已与 moxuanag 确认）——那会把两套能源合并，Botania 的独立价值就没了。

修复是本体系的第二大消耗口：装备修补按 HP 扣魔力，详见第二部分 §7 修复器。

## 8. 配方简化规则与数值基线

1. **成品原料 ≤ 2 种**（不含魔力，魔力从池里扣，不占背包）；
2. **不做三级以上链条**：矿石 → 锭 → 零件 → 成品，最多两级；
3. **门槛靠研究与设施**，不靠新材料：新东西要么是「新研究」，要么是「新工作台」，要么两者；
4. **同一台设施做一类事**：花瓣祭坛做花、灌注台做材料、精灵门做交易——不为单件物品新开工作台；
5. **工时是主要成本**：工业级装备 4–6 小时，太空级 12–16 小时。让玩家用殖民地的「时间」而不是「背材料清单」感受进度。

---

| 项 | 建议值 | 参照 |
|---|---|---|
| 研究点 | 300 / 600 / 900 / 1200 / 1500 / 1800 / 2000 / 2400 / 3000 / 3500 / 4000 / 5000 | 原版中世纪科技 400–1000，太空科技 2000–4000 |
| 火红莲 | 30 魔力/秒 | 现有 |
| 地热火莲 | 60 魔力/秒 | 间歇泉是稀缺地块，翻倍合理 |
| 魔力池 | 10 万（现有）/ 扩容 25 万 | 现有 |
| 通量场 | 1000 W，效率 90% | 现有 |
| 法杖 | 50 魔力/发（杖内储 500） | 一发 ≈ 1.7 秒火红莲产能 |
| 装备工时 | 4–6 h（工业）/ 12–16 h（太空） | 原版长弓 4h、海军甲 60h 之间 |

// 1) wornGraphicPath 留空 → 直接不画外观，不报错、也不退回物品图标
if (apparel.WornGraphicPath.NullOrEmpty()) { rec = new ApparelGraphicRecord(null, null); return false; }

path = apparel.WornGraphicPath + "_" + bodyType.defName;   // 例：_Male

实现口径（**必须成对写**，否则引擎直接报配置错误）：

```xml
<!-- ResearchProjectDef -->
<techprintCount>1</techprintCount>
<heldByFactionCategoryTags>
  <li>BotaniaGaiaBoss</li>
</heldByFactionCategoryTags>
```

- 引擎的成对校验（`ResearchProjectDef.ConfigErrors`，已反编译核对，2026-10-23）：
  - `techprintCount > 0` 而 `heldByFactionCategoryTags` 为空 →
    `requires techprints but has no heldByFactionCategoryTags.`
  - `techprintCount == 0` 而写了 tags →
    `requires no techprints but has heldByFactionCategoryTags.`

- tags 里写什么：**这套引擎里它只是一个字符串**（没有 `FactionCategoryDef` 类型，

  表意即可，不会真去匹配派系，也就不会变成商人货架上的东西；
- 蓝图 ItemDef 挂**两个** comp：
  - `CompProperties_Techprint { project: Botania_Gaia }` —— 数据层，
    `ResearchProjectDef.Techprint` 靠反查它找到蓝图物品，
    缺了会 `Log.ErrorOnce: Could not find techprint for research project`；

盖亚祭坛（3×3）+ 50,000 魔力 + 1 泰拉钢锭；仅夜间或雷暴可召唤（强化仪式感）。

#### 实现路径（实施前要用反射核对）

| 需求 | 打算怎么做 | 要核对的点 |
|---|---|---|
| 本体 | `PawnKindDef` + `ThingDef`（Race） | 引擎是否支持 `PawnKindDef.abilities` 直接挂能力 |
| 弹幕 / 瞬移 / 召唤 | 原版 `AbilityDef` | 1.7 的 Ability 系统给敌人怎么授予（PawnKind 字段 vs HediffComp） |
| 领域压制 | 给范围内小人挂负面 `HediffDef` | 得用 `statOffsets` 影响 `RangedWeapon_DamageMultiplier` 之类 |
| 魔力爆裂 | `ThingDef` + 延迟爆炸 Comp | 参考原版地雷 / 燃烧弹的实现 |
| 阶段切换 | 常驻 `HediffDef` + 检查 HP 比例 | 引擎里 Pawn 的 tick 钩子（`Tick` 覆写 vs Comp） |

> 风险最高的就是这块：Boss 手感、召唤平衡、存档兼容都要单独测。这也是先延后的原因。

## 12. 特殊结构（手动搭建的清单）

Botania 的仪式感有很大一部分来自「自己搭一个东西」，而不是点一下造出来。这一节定义哪些东西按「结构」做，以及为什么它排在敌人之前。

### 什么算结构

- 占多格（2×2 以上），放下就能看出是个装置；
- 需要玩家自己选位置、对齐，甚至围着它摆别的部件；
- 有「激活 / 未激活」两态，靠组成条件判定。

### 清单（按版本）

| 结构 | 时代 | 组成 | 作用 | 版本 |
|---|---|---|---|---|
| 花瓣祭坛 | E1 | 2×2 单件 | 批量制花，消耗花瓣与魔力 | v0.5 |
| 泰拉凝聚台 | E3 | 3×3 主体 + 四周四个基座 | 产出泰拉钢 | v0.7 |
| 精灵门 | E3 | 5×3 门框（左右柱 + 上梁），中间留空 | 用魔力换精灵材料 | v0.7 |
| 盖亚祭坛 | E3 | 3×3，半径 6 内不允许有其他结构 | 召唤盖亚（第一部分 §11） | v0.8 |

### 实现口径

- **首选**：单个多格 Def + Comp 检查邻接——简单、存档稳，不需要额外「蓝图组合」系统；
- **次选**：每个部件独立 Def + 中心 Comp 汇总——更灵活，但摆错时的提示必须做足；
- **不建议**：要求玩家按固定图形摆 N 个方块的玩法——环世界的放置体验撑不住那套精度。

### 为什么排在敌人之前

结构是装备与建筑的终点，也是 Boss 的载体（盖亚祭坛）。先把结构做稳，Boss 只要「接在祭坛上」；反过来先做 Boss，会逼着结构为战斗临时改设计，等于白做一遍。

## 13. 材料、符文与遗物

### 材料谱系（改）

原版 Botania 的**魔力钻石 / 魔力珍珠不做**。魔力阶材料只保留两种：

| 材料 | 时代 | 来源 | 用途 |
|---|---|---|---|
| 魔力钢 Manasteel | E2 | 钢铁 + 魔力尘 + 魔力 | 装备主力材料、机械部件 |
| 魔力玻璃钢 Mana Glass | E3 | 魔力钢 + 玻璃 + 魔力 | 高级装备、精灵门的透镜与框架 |

> 为什么是玻璃钢而不是钻石/珍珠：环世界本来就有玻璃与钢铁工业，玩家对「玻璃钢 = 高级复合材料」有直觉；钻石/珍珠在环世界里没有对应产业链，硬塞会显得突兀。

### 符文（缩减为 9 枚）

| 档位 | 数量 | 获取 | 用途 |
|---|---|---|---|
| 基础符文 | 4 | 商人购买 / 遗迹挖掘 | 中级配方、设施升级 |
| 高级符文 | 2 | 遗迹挖掘（罕见）/ 高价购买 | 高级装备与结构 |
| 终极符文 | 3 | 只能遗迹挖掘（极罕见） | 泰拉钢、盖亚祭坛 |

- 符文**不做合成**：原版 Botania 靠符文祭坛合成，这里改成「买 / 挖」，直接砍掉一条合成链；
- 符文的稀有度就是软门槛——玩家挖到 3 枚终极符文，才知道终局长什么样。

### 遗迹与远行遗物

| 物件 | 获取 | 机制 |
|---|---|---|
| 始祖花 | **远行**（世界地图事件）里遇到的彩蛋 | **就地取能**：使用后当场产出大量魔力；**移动即自毁**——被搬运、装运或带离地块就消失 |
| 增生之种 | 遗迹 | 种植后把周边土壤肥力提升一档，一次性 |
| 植物魔法词典 | 遗迹 / 商人 | **不能阅读**（不做书籍 UI）；**放在研究台 3 格内**时，该台研究本 mod 项目 +20% |

> 始祖花的设计意图：它是「远行补给」，不是能搬回家的发电机。玩家得为一次远征专门规划——用不用、什么时候用。

### 为什么这些东西不给合成

符文、始祖花、增生之种、词典都是**发现品**：价值来自「你走到了哪里」，不是「你攒够了什么」。做成合成品，远行与挖掘的动机就被抽掉了。

## 2. 魔力网络：一切机制的地基

**接口** `IManaSource`（`Source/IManaSource.cs`）：`ManaAmount`、`FreeSpace`、`AddMana`、
`DrainMana`；配套 `ManaSourceUtil.FindNearest(origin, map, radius, needAtLeast, exclude)`，
「找最近的、至少能给这么多的源」——所有耗魔设备都用它，不要自己遍历。

| 实现者 | 容量 | 特点 |
|---|---|---|
| `CompManaStorage`（魔力池） | 简易 2000 / 大池 100000 | 紧贴的池子每 4.2 秒均摊；供给半径 6 |
| `CompManaRelay`（中继塔） | 自身缓冲 6000 | 半径 8、40 魔力/秒，每跳损耗 10% |
| 六朵产能花 | 各自缓存 | 见下章 |

> 断供语义**不是统一的**：有的设备断魔降速继续（白雏菊），有的必须停（精灵之门）。
> 写新设备前先想清楚它属于哪一类。

## 5. 精灵之门（`Botania_Alfheim` · 3500 · 前置魔力灌注）—— 已实装

> 2026-10-23 实装，**同日实机验证通过**（建造、缺柱拦截、投料转化、断魔即停均正常）。

> **2026-10-23 定稿并实装**，与初稿的三处改动见每节末尾的「改了什么」。

### 解锁清单

| 内容 | 类型 | 说明 |
|---|---|---|
| 精灵门 | 结构（三件套，总占 5×3） | 上梁 3×1 + 左柱 1×3 + 右柱 1×3，门洞 3×2 **真的留空、可通行** |

### 运作方式

### 数值（已实装）

### 改了什么（相对初稿）

1. **Bill → 投料自动转化。** 这套引擎没有干净的「Bill 扣魔力」接入点
   （`RecipeDef` 不认魔力，而自定义 JobDriver **实测不生效**），
   硬做只能每 tick 扫「谁在这个台子上干活」，太脆。改为复用白雏菊那套转化思路，
   但重写成 `CompManaGate`：白雏菊的「断魔降速免魔」语义对门是错的，门必须停。
2. **5×3 实心 → 三件套真门洞。** 环世界的 `size` 是实心矩形，没法在 5×3 里挖洞。
   拆成上梁 + 左右柱之后，中间 3×2 是真空地，人能走过去，也更像门。
3. **精灵石英的输入从「玻璃 ×4」改成「活石 ×4」。** 环世界根本没有玻璃这个物品
   （`defName` 里一个都搜不到），原来的配方式立刻卡死；活石是白雏菊就能产的东西，
   且「把石头养成水晶」在设定上更顺。
4. **建造材料改掉循环依赖。** 初稿要「梦木 ×12 + 精灵石英 ×8」，而这两样正是门的产品，
   等于要求先有门才能建门。改成全部来自门之前的科技。

## 12. 开发流程与校验工具

1. 改 C# → 在 `Source/` 下 `dotnet build -c Release`（**游戏开着会锁 DLL**），
   确认 `Assemblies/Botania.dll` 比最新 `.cs` 新；
2. 跑 `_dev/_botania-dev/validate_mod.py`，必须打印「全部检查通过。」；
3. 提交：`git commit -F <消息文件>`（带括号/引号的消息别写进 `-m`）；
4. 推送：走 Clash 代理 `git -c http.proxy=http://127.0.0.1:7897 push ...`，别把代理写进仓库配置。

### 分支与合并（2026-10-24 定，**每轮都照这个走**）

**新功能一律先开 `feat/xxx` 分支提交，验完再 `--no-ff` 合进 `main`；禁止再直接往 `main` 提交。**

```
git checkout -b feat/xxx          # 从当前 main 开分支
...   # 改代码 / 出图 / 改文档，按上面 1–2 步校验
git add -A && git commit -m "..."
git push <远端> feat/xxx:feat/xxx
git checkout main
git merge --no-ff feat/xxx -m "merge: feat/xxx → main（一句话说明）"
git push <远端> main:main
```

- 为什么必须 `--no-ff`：`main` 上要能一眼看出「这一坨是哪个功能、什么时候合的」。
  fast-forward 会把功能提交拍平进主线，历史里看不出边界；
- 为什么不能直接提 `main`：这一步是 2026-10-24 补的规矩。泰拉钢那次直接提在 `main` 上，
  事后再建同名分支合并，git 只会回一句 `Already up to date`，**留不下 merge 记录**；
- 分支**不删**：远端保留 `feat/xxx`，和茶叶协作时的习惯一致，方便回溯某一版的完整改动；
- 文档/贴图这类收尾提交也走分支（`docs/xxx`、`art/xxx` 同理），免得主线上出现零散提交。

校验器目前会拦：Def 交叉引用、本地化覆盖、`DefInjected` 字段存在性、
`stuffAdjective` 中文注入、产业链可达（含精灵门的多输入规则）、
不可通行建筑的 `fillPercent`、护甲引用的 `BodyPartGroupDef` / `ApparelLayerDef`、
贴图尺寸/透明度、DLL 里的自定义类型清单。

### 交给玩家测试时的交付格式（**硬性要求**）

每次说「你去测一下」，必须同时给出：

1. **`defName` 清单**，一行一个，中文名 ↔ defName → 用途/怎么测；
2. 拿到的办法：开发者模式 → **生成物品**（Spawn thing），搜中文名或直接输 `defName`；
   要按正常流程测就再给研究项 `defName`；
3. 预期表现 + 具体要看什么（好看坏、哪个数字、哪个按钮）。

原因：玩家在游戏里只能靠**中文名**搜索，而不同模组可能有同名物品（比如 `[CY]Botania`
的 `Botania_*` 和我们的重名），只给中文名会搜出别人的东西；只给 defName 又不方便手输。
两边都给，才测得到我们这一份。

## 13. 元素装备与精灵灯（2026-10-24）

| 物品 | 写法 | 要点 |
|---|---|---|
| 元素剑 | `BaseMeleeWeapon_Sharp_Quality` + `costList` | 不用 `costStuffCount`（元素锭不是 stuff 类别的替代品，直接列料） |
| 水晶弓 | `Verb_ManaBolt` + `CompProperties_ManaWeapon` | 和法杖共用同一套扣魔逻辑，只是弹丸换了 `Botania_CrystalArrow` |
| 元素甲 / 盔 | `ApparelBase` + `<apparel>` | **不写 `wornGraphicPath`** 就是「无外观但不报错」；`graphicData.texPath` 仍给物品图标 |
| 精灵灯 | `LampBase` + `CompManaPixieLamp` | 见下 |

**精灵灯为什么不用反射改 `CompGlower`**

原版灯本来就有 `CompFlickable`（玩家手动的开关），`CompGlower` 会跟着开关状态亮灭。
所以 `CompManaPixieLamp` 只做三件事：

1. 每 60 秒向 8 格内的魔力源要 1 点魔力（`ManaSourceUtil.FindNearest` + `DrainMana`）；
2. 把「要到了没有」翻译成 `CompFlickable.SwitchIsOn`；
3. 断魔 → 拨到关；来魔 → 拨回开。检视栏给一行状态。

好处是**完全不碰引擎内部**：不反射、不覆写 `ShouldBeLit`、也不用自定义 `CompGlower` 子类。
代价是玩家手动拨开关会被下一次结算覆盖——对「按魔力自动亮灭」的设备来说这是想要的行为。

结算节奏（2026-10-24 实机反馈后调整）：

- **建好立刻结算一次**：没魔力的话当场就是暗的，不再「先亮一会儿」；
- 亮着时**每 60 秒**扣 1 魔力；
- 熄着时**每 5 秒**再看一眼：池子搬到旁边后几乎立刻亮，而不是干等一分钟。

### 披挂图（2026-10-24 补）

RimWorld 的披挂图不是一张，而是：

- `<apparel><wornGraphicPath>路径</wornGraphicPath>`；
- 引擎拼的是 `wornGraphicPath + "_" + bodyType.defName + "_" + 方向`，
  **必须按体型分文件，且没有回落**——缺一张就在渲染那一帧报
  `Failed to find any textures at ..._Male`；
- 方向只有 `_north` / `_east` / `_south`（**西向由东向镜像**，不用画）。

所以一件护甲 = **6 体型 × 3 方向 = 18 张图**。体型之间的差别用缩放近似
（Thin 0.90、Fat 1.14、Hulk 1.26、Child 0.62，脚底对齐 y=120），
图由 `_dev/_botania-dev/gen_worn_armor.py` 生成，以后有美术再替换。

> 曾经判断错的一次：工坊里 `RK_BulletProofHelmet` 只有三张无体型图，
> 我据此以为「不按体型也能共用」——**错的**，引擎不做回落，见踩坑第 12 条。

### 装备态魔力 UI：必须接管 `CompEquippable`

引擎里「已装备物品」的 Gizmo 出口是 `CompEquippable.CompGetEquippedGizmosExtra()`。
只挂 `CompManaWeapon` 的话：**放在地上看得见魔力储备，拿在手里什么都没有**——
因为 `CompManaWeapon.CompGetGizmosExtra()` 走的是「物品自己的 Gizmo」那条路。

所以任何带魔力的武器都要：

1. `<comps Inherit="False">` 整段接管，并放 `Botania.CompProperties_Equippable_Wand`，
   保证武器身上只有一个 `CompEquippable`；
2. 把父模板链上的组件一个不漏抄全（Forbiddable / Styleable / Art / Quality / Biocodable），
   漏一个就是配置错误（漏 Styleable 会报 `IdeoRelic missing CompStyleable`）。

> **自检**：新武器实装后，先看「拿在手里」有没有魔力条和「充能」按钮，再看打不打得出去。

### 面板护甲值为什么不是 90%

护甲面板是**全身加权平均**，不是每件装备的标称值。元素甲覆盖躯干·颈·肩·臂·手·腿·足，
唯独没有头，所以只穿甲实测 **71% / 35%**；戴上头盔（`FullHead`）会再升一截，
但仍然不等于 90%——90% 是「被覆盖部位」的值，不是面板值。

### 建造入口

两者都可收纳（`minifiedDef`），拆下来能搬走。

### 四角提示（结构感，2026-10-24 玩家要求）

玩家不可能靠猜知道「基座要摆在对角那一格」，所以**蓝图阶段就要画出来**：

| 场景 | 画什么 | 颜色 |
|---|---|---|
| 放置 / 移动蓝图（还没建） | 四个对角格 | 已有基座=绿、空位=天蓝、被别的建筑占住=橙 |
| 选中已建成的凝聚台 | 四个对角格 | 已有基座=绿、缺的黄 |
| 选中还没盖的凝聚台蓝图 | 四个对角格 | 全黄（等于「这四处都要建」） |

三个入口共用同一份几何：`TerraAltarCorners.Of(CellRect)`。
放置预览走 `PlaceWorker_TerraPedestals`，选中态走 `MapComponent_Rings`
（和魔力池的范围环同一套机制：建筑的 `Draw` 不一定调到 `Comp.PostDraw`，
所以「选中时的提示」统一放 MapComponent 里画）。

**引擎坑**：`PlaceWorker.DrawGhost` 传进来的 `center` 是**占用区的中点**
（3×3 时就是正中那格），不是左下角。再按 `size` 偏移一次，整组提示会跑到右上角。

#### 材料怎么上台（2026-10-24 玩家提问 → 已改成搬运工作）

**最初的实现是错的路径**：第一版做成「点建筑 → 按钮 → 轮到某个闲人」——`Command_Toggle`
+ 每 60 tick 轮询 + `TryTakeOrderedJob` 手动插队。玩家问了一句「为什么不能直接用搬运工作」，
点破了两件事：

1. 「自定义 JobDriver 不生效」（踩坑第 3 条）**不适用于 WorkGiver**——只要 WorkGiver 交回去的是
   **原版** `JobDefOf.HaulToCell`，司机是原版的，我们根本不需要自己实现走路/抓取/放下；
2. 自己轮询 + 插队，等于把原版的工作调度、优先级、打断逻辑全部绕开重写了一遍，
   必然比原版更差（第一版甚至用 `curJob == null` 判闲人，永远等不到人，见踩坑第 20 条）。

**现在的做法（正确做法）**：`WorkGiver_TerraAltarDeliver : WorkGiver_Scanner`，
挂在原版 **Hauling** 工作类型下，和「运材料给蓝图 / 框架」完全同类：

| 项目 | 值 |
|---|---|
| `WorkGiverDef` | `BotaniaDeliverToTerraAltar`（`Defs/WorkGiverDefs/WorkGivers_Botania.xml`） |
| `workType` | `Hauling`（所以玩家关掉某人的搬运，他就不会来送料） |
| `priorityInType` | 8（比运给蓝图 9 略靠后，别抢工地供料） |
| `giverClass` | `Botania.WorkGiver_TerraAltarDeliver` |
| 交回的 job | **原版** `JobDefOf.HaulToCell`，`job.count` = 缺口数量，`haulMode = ToCellNonStorage` |

台子上的开关（`Command_Toggle`「允许搬运工送料」，**默认开**，状态进存档）只是许可位：
关掉 = 这条工作对这座台子不成立，小人不会来送；打开 = 交给搬运工作自己调度。

**落点**：台面**外圈八格**里最空、且**还没被别人预定**的一格。中心 `CenterCell`
是 `FinishIngot` 的产出格，材料堆中心会挡住产出（踩坑第 21 条）。

「没被预定」这条是必须的：原版 `JobDriver_HaulToCell` 会**预定目标格**（maxPawns 1），
几个搬运工被派到同一格时，第二个必然报
`Could not reserve ... for job HaulToCell` 然后站着不动（踩坑第 22 条）。
外圈有八格，各自挑自己预定得到的格，就能并行送料。

**送料前提**：四角基座齐全（`MissingPedestals == 0`）才送料，否则材料堆一台子却没地方用。

**判断「能不能送」的三道关**（都在 `TerraAltarHauling.TryPlan` 里）：
台面真缺这种料（`TryGetNeed`，口径与生产判定共用）→ 有小人在本图、够得着、能预备的一摞材料
→ 台面上有个能站、走得到、**自己预定得到**、尽量空的落点。

**实机验证（2026-10-24 20:05，玩家确认）**：多个搬运工并行送料正常，
日志里不再出现 `Could not reserve ... for job HaulToCell` / `TryMakePreToilReservations() returned false`。
送料这条链路从「按钮轮询」改成「原版搬运工作」后，至此闭环。

#### 一键补齐四角基座（2026-10-24 玩家要求）

光有「该放哪儿」的提示还不够——玩家还得自己去建造菜单里翻基座、对格子。
所以选中凝聚台时给一个按钮（`Command_Action`），点一下就在缺的角上**直接放蓝图**：

- 已有基座、或已经有基座蓝图的角**跳过**（不会重复刷蓝图）；
- 每格先过 `GenConstruct.CanPlaceBlueprintAt(def, cell, Rot4.North, map, false, null, null)`，
  不接受就计入「放不下」，不硬塞；
- 真正落蓝图用 `GenConstruct.PlaceBlueprintForBuild(def, cell, map, Rot4.North, Faction.OfPlayer, null)`；
- 结果是两条提示：放了几根 / 几个角放不下（被占或地形不允许）；
- 按钮变灰的条件是「**既没有实心基座、也没有基座蓝图**」的角为 0——
  注意这和「罢工判定」不是一回事：蓝图能被工人盖出来，但不能当作已有基座（生产必须实心）。

这就是原版那种「点建筑 → 按钮 → 附属件自动摆好」的体验，机制上是 `Command_Action` +
`GenConstruct`，不需要自定义 Designator。

### 凝聚台怎么判定

- 四角基座：取 3×3 的四个对角格，逐格找 `Botania_TerrasteelPedestal`，**少一根就开工不了**
  （检视栏直接写还缺几根，不用玩家猜）；
- 材料：`parent.OccupiedRect()` 里扫 `魔力钢锭` 与 `精灵石英`，够数才开工；
- 魔力：`ManaSourceUtil.FindNearest` 找 8 格内 ≥ 20,000 的源，**开工时一次性扣掉**
  （不是按 tick 摊，避免中途断电留下半成品）。
  这条**硬门槛不迁就简易魔力池**（2,000）：简易池是前期过渡建筑，泰拉钢是终局内容，
  该配 3×3 魔力池（100,000）或中继塔链——2026-10-24 玩家确认「简易魔力池前期过渡用的，不用管」；
- 2,400 tick 后在台心 `GenPlace.TryPlaceThing` 出一枚锭；
- `progress` / `running` 进存档，读档能接着走。

### 剑气为什么做成技能而不是「武器第二个 Verb」

让一把近战武器同时拥有远程 Verb，会让小人在征召状态下改用远程攻击，
近战武器就废了。改成 `Ability_TerraWave`（照原版灵能那套：
`abilityClass` 指自定义 Ability 子类 + `Verb_CastAbility`，**不自定义 Verb**），
**命中规则（2026-10-24 玩家改定）**：只放过**自己人、自家动物、自家建筑**；
中立/敌对的人、动物、建筑全部吃伤害。写法是白名单——只有「玩家阵营」免伤，
其余一律结算，不再靠 `Faction == caster.Faction` 这种间接判断。
地上的物品、石块、泥土不参与结算（`ThingCategory` 只认 Pawn / Building）。

**瞄准预览（同日改）**：点技能后**不再显示原版蓝色准星**，改画两样东西——
施法者身上的 **12 格射程圈**，以及**剑气实际会扫过的那 12 格**（落点再单独标一格）。
两者共用 `TerraWavePath.Cells`，预览和结算不会对不上。
实现是 `Verb_TerraWave : Verb_CastAbility`，重写 `DrawHighlight` 且**不调 base**
（base 依赖 ability 状态，一抛异常整层 GUI 消失），整段包 try/catch。
自定义 verb 还要在 `Ability_TerraWave` 构造时补 `cast.ability = this`，
否则 `Verb_CastAbility.OnGUI` 每帧 NRE。详见踩坑 #23。

**不耗魔力，只吃 8 秒冷却**（2026-10-24 玩家改定）。原先扣「附近魔力源」400 魔力，
问题是装备态**没有魔力条**：玩家按下去没反应，只会以为技能坏了。
要么加一条得额外解释的 UI，要么干脆照原作 Terra Blade 的手感——挥出去就有。
玩家选了后者。

由 `MapComponent_WandState` 按「手里有没有 `CompTerraBlade`」授予/收回——
和法杖给「绽花 / 就地转化」是同一个机制，卸下武器技能自动消失。

- 直线 12 格，伤害 `Lerp(30, 10)` 逐格递减，穿透 0.45；
- 一次抽 400 魔力，冷却 480 tick（8 秒，写在 `cooldownTicksRange`）；
- **不误伤**：同阵营的 Pawn 与建筑直接跳过；
- 表现：每格 `FleckMaker.ThrowDustPuff` + `ThrowLightningGlow`。

### 踩到的坑（含首次实机加载报错）

1. `Graphic_StackCount` 的 `texPath` **必须是文件夹**，写成具体文件会
   `Collection cannot init`；文件按 `<名字>_a/_b/_c.png` 放在该文件夹下。
2. `equippedStatOffsets` 只做**加算**：想要 ×1.5 就写 `MiningSpeed +0.5`
   （基础值 1.0），而不是写 1.5。
3. `<passability>` 写了 `Walkable` → **整份 XML 不加载**（详见踩坑第 16 条），
   连带 `DefInjected` 里这个名字的翻译报「Translation data ... has 2 errors」。
   真值只有 `Standable` / `PassThroughOnly` / `Impassable`。
4. 基座可收纳却没写 `thingCategories` → `is minifiable but not in any thing
   category`（踩坑第 18 条）；两个新建筑都补了 `BotaniaBuildings`。
5. `AbilityDef` 的 `hotKey` 写 `Misc13` → `Could not resolve cross-reference`
   （踩坑第 17 条）；剑气**干脆不写 hotKey**，靠技能栏点。
6. 自动搬运第一版用 `curJob == null` 判「闲人」→ **永远等不到人**，
   因为原版待命的小人挂着 `Wait` / `Wait_Wander`（踩坑第 20 条）。
7. 材料落点写成「台面中心」→ 正好压在泰拉钢的产出格上（踩坑第 21 条）。

### 碎岩镐的 3×3 同步采矿（2026-10-24 玩家要求）

装备泰拉碎岩镐采矿时，**正在挖的那格和周围八格同步掉耐久**，等于一次挖 3×3。

**按百分比同步，不按绝对耐久**（2026-10-24 玩家给的例子定的口径）：
中心 2000 耐久的压埋机械、外圈 400 耐久的砂岩，**挖完中心那一刻外圈同时挖完**。
按绝对伤害同步会让 400 的砂岩早早崩掉，不符合要求。

`CompTerraPick` 每 15 tick 做一件事：

1. 算中心格完成度 `progress = 1 - 中心.HitPoints / 中心.MaxHitPoints`；
2. 对周围八格逐个算「要打到相同完成度还差多少伤害」
   （`damage = 本格.HitPoints - 本格.MaxHitPoints * (1 - progress)`）；
3. 差多少打多少（`Mineable.TakeDamage(Blunt)`）；
4. 中心被挖穿后，周围直接补满——九格同一刻崩。

这样无论耐久差几倍、石种多杂、小人技能多高，九格永远同时挖完；
装了改采矿速度的模组也自动跟着走（因为我们照抄中心进度，不自己拍伤害数）。

- 只对 `Mineable`（自然岩石/矿脉）生效，**不会顺手啃掉玩家自己的墙**；
- `requireDesignation` 默认 `false`（不要求相邻格划过采矿标记）；想「只挖划了标记的」就设 `true`；
- 掉落走原版销毁流程（每格各自掉自己的产物）；
  开发者模式下会打「挖穿 def（应掉 N）」和「实际掉落：产物 ×数量（几堆）」两行日志，
  用来核对「外圈只掉一个矿」这类问题。

**必须写 `<tickerType>Normal</tickerType>`**：物品不写就永远不 tick，整个机制静默失效
（和老坑「自充能全失效」同一个原因）。

### 1. 建材盖出来的东西中英混排：「dreamwood 墙」

**日期**：2026-10-23（实装梦木 / 元素锭时踩到）

**现象**：用梦木、元素锭盖的墙显示成 `dreamwood 墙`、`elementium 墙`；
活木墙、魔力钢墙一直正常。

**原因**：带材料的物品名字由 `Thing.LabelNoCount` 拼：

```csharp
stuff.LabelAsStuff + " " + def.label
```

而 `ThingDef.LabelAsStuff` 直接返回 `stuffProps.stuffAdjective` 的**原文**，
不经过 Def 的 label 翻译。所以 `label` 翻译了也没用，`stuffAdjective` 必须单独注入。

**定性做法**：凡是写了 `<stuffAdjective>` 的建材，都要在
`Languages/ChineseSimplified (简体中文)/DefInjected/ThingDef/Botania_Things.xml`
里补一条：

```xml
<Botania_Dreamwood.stuffProps.stuffAdjective>梦木</Botania_Dreamwood.stuffProps.stuffAdjective>
<Botania_ElementiumIngot.stuffProps.stuffAdjective>元素</Botania_ElementiumIngot.stuffProps.stuffAdjective>
```

**防复发**：`_dev/_botania-dev/validate_mod.py` 的 `check_stuff_adjectives()`：
凡是带 `stuffAdjective` 的模组 ThingDef，中文缺注入直接 FAIL 并点名。
（已自测过：删掉元素锭那条会立刻报出来。）

### 2. 科技蓝图的整条链路都挂在皇权 DLC 上

**日期**：2026-10-23（实装盖亚之魂蓝图时确认）

**现象**：没装皇权 DLC 时，蓝图右键没有任何选项，等于一张废纸。

**原因**：三处 DLC 门，反编译逐一确认：

```csharp
// 1) 菜单入口
if (!ModLister.CheckRoyalty("Techprint")) yield break;      // CompTechprint.CompFloatMenuOptions
// 2) 真正的应用逻辑
if (!ModLister.CheckRoyalty("Techprint")) return;           // ResearchManager.ApplyTechprint
// 3) 结束时的音效：TechprintApplied 定义在 Royalty/Defs/SoundDefs/UI_OneShots_Misc.xml
SoundDefOf.TechprintApplied.PlayOneShotOnCamera();          // 没装时为 null → NRE
```

**定性做法**：**不要用 Harmony 去补这三处**（补一处就得补一串，还会剩下 null 音效），

**顺带记住**：`heldByFactionCategoryTags` 在这套引擎里**只是一个字符串列表**，

检查空/非空），所以随便填个表意名字即可，不会真的去匹配派系。

### 6. 建筑的 `size` 是实心矩形，做不出「中间留空」

**日期**：2026-10-23（实装精灵之门时确认）

**现象**：想做一扇「两根柱子 + 上梁、中间能走人」的 5×3 门，
把 `size` 写成 `(5,3)` 之后，中间三格也一起被建筑占了，人过不去。

**原因**：`ThingDef.size` 描述的是**实心占用区**，引擎没有「这个矩形里哪几格是空的」这种表达；
`passability` 也只能整栋一起设，不能只让中间可通行。

**定性做法**：拆成多个 Def 拼装 —— 精灵之门是
「上梁 `(3,1)` + 左柱 `(1,3)` + 右柱 `(1,3)`」，中间 `3×2` 不摆任何东西，天然通行。
代价是要建三次，所以：

- 上梁挂 `CompManaGate`，并配 `framePillarDefs` 列表，**每 tick 检查两端立柱是否齐全**，
  缺柱时门完全不工作、检视栏直接写「门框不完整」；
- 放置时用 `PlaceWorker_GateFrame` 把两根柱子的位置画成绿框，玩家照着摆。

**顺带记住**：多格建筑的贴图尺寸 = **格数 × 128**（上梁 3×1 → 384×128，立柱 1×3 → 128×384），
`drawSize` 也要跟着写 `(3,1)` / `(1,3)`。

### 8. 不可通行且可建造的建筑，`fillPercent` 必须 = 1

**日期**：2026-10-23（精灵之门首次进游戏报错）

**日志原文**：

```
Config error in Botania_AlfheimGateLintel: impassable, player-buildable building that can be shot/seen over.
Config error in Botania_AlfheimGatePillarLeft: 同上
Config error in Botania_AlfheimGatePillarRight: 同上
```

**原因**：精灵门的三个件沿用了现有建筑的 `<fillPercent>0.50</fillPercent>`，
但那几个建筑是 `PassThroughOnly`（人能穿过去），填 0.5 没问题。
门框是 **`Impassable` + 玩家可建造**，填 0.5 就自相矛盾：
人过不去，子弹和视线却能飞过去。引擎在 `DefDatabase.ErrorCheckAllDefs` 里直接判错。

**规律**（扫了原版 41 个 `Impassable` 建筑确认）：
玩家可建造的那几个——墙、地热发电机、污染发电机——**全部 `fillPercent = 1`**；
而 `fillPercent < 1` 的（`MechStabilizer` 0.5、`AncientHatch` 0、Fleshmas 系列 0.75）
**全部不可建造**。

**定性做法**：`Impassable` + 进建造菜单的建筑，`fillPercent` 写 `1`。

**已经加进校验器**：`check_impassable_fill()`。
它沿 `ParentName` 链取生效的 `passability` / `fillPercent`，
对「有 designationCategory + 有 building + buildable 不为 false + Impassable + fillPercent < 1」报错，
报错文案直接带上引擎原文，方便对上日志。已反向验证过（把 0.5 写回去能拦下三条）。

**顺带**：这类错误**不影响游戏启动**，只是 Def 加载时刷红字、建筑照常能用，
所以很容易被忽略——看到 `Config error in <你的Def>` 一定要当回事。

### 9. 想监听「完成一次工作」，job 结束和成品产出都不是锚点

**日期**：2026-10-23（苦丽花连续三版才抓准）

**现象**：苦丽花的设计是「小人完成一件工作 → 花产魔力」。名字叫 `DoBill` 的账单活
（缝制、屠宰、做饭）怎么都不触发，而**建造屋顶、采矿**这类活却正常。

**原因**：

1. `Pawn_JobTracker.EndCurrentJob` 只在 **job 结束**时触发。而账单活是
   「一张单连续做很多件」——做完一件，pawn 还挂在同一个 job 里，
   只有做满整张单（或被打断）才结束，所以这条路永远等不到「做完一件」。
2. 退而去挂 `GenRecipe.MakeRecipeProducts`（每产出一件成品调一次）也不稳：
   它依赖具体的产出路径，某些工作台 / 特殊 recipe 不走这条，实测缝制仍然没触发。
3. 教训：**job 的生命周期 ≠ 劳动的完成**。想在「干完一点活」这个粒度上做事，
   需要找一个**每次劳动都会产生的副产物**。

**定性做法**：监听技能经验 `Pawn_SkillTracker.Learn(SkillDef, float xp, bool, bool)`：

- 任何算得上劳动的行为都会涨经验（建造、采矿、缝制、屠宰、锻造、研究…），
  不需要给工作类型列白名单，也不会因为模组工作台换实现而漏；
- 经验还是**天然的计价单位**：盖屋顶只涨 1–3 点，缝一件衣服涨 25–40 点，
  「干多少活给多少产出」直接按经验折算即可（苦丽花：`min(400, 经验 × 10)`）；
- 需要 pawn 时用 `__instance.GetSkill(skillDef).Pawn`（`SkillRecord.Pawn` 是公开属性），
  `Pawn_SkillTracker` 自己**没有**公开的 pawn 字段。

**防复发**：凡是「按劳动量结算」的需求（产能、耐久、疲劳、熟练度），
优先找经验的来源；确实需要 job 级别的信号时，先问一句
「这个 job 是干完一次就结束，还是会连续干很多次」。

### 13. 弹丸贴图的基准方向是**北**，画成朝东会被再转 90°

### 14. 合并别人的分支时，`DefInjected` 可能被整体覆盖（丢翻译）

**日期**：2026-10-24（合并 `feat/life-orchid`）

**现象**：合并本身没报冲突，`git diff --stat` 只显示该文件「+3 / −9」，

`以下 Def 缺少中文 DefInjected 条目：['RecipeDef:Botania_MakeManaPowder', ...]`。

**防复发**：校验器的本地化覆盖检查保持「缺一条就 FAIL」，不降级成警告。

### 20. 想找「闲着的」小人，不能判 `curJob == null`

**现象**：开关打开了，检视栏一直显示「等一个闲着的搬运工」，没有任何小人来搬。

**原因**：原版**待命的小人也有 job**——`JobDefOf.Wait` / `Wait_Wander` / `GotoWander`。
所以 `pawn.jobs.curJob == null` 在正常基地里几乎永远为 false，条件等于「要求全殖民地停摆」。

**定性做法**：判「闲到可以派活」= `curJob == null` **或**当前 job 属于原版的等待/闲逛一组
（`Wait` / `Wait_Wander` / `Wait_Downed` / `GotoWander` / `Wait_MaintainPosture`）。
要打断真正的工作时，另开开关，别偷偷插队。

### 21. 台面中心是**产出点**，送料不能放中心

**日期**：2026-10-24（玩家指出）

**现象**：按第一版实现，材料被搬到台面正中；结果成品（`FinishIngot` 用
`OccupiedRect().CenterCell`）就生成在同格，被材料挤开甚至看着像「没产出」。

**原因**：我图省事用了 `CenterCell` 当落点，而它同时是产出格。

**定性做法**：送料落点取台面**外圈八格**里最空的一格（`Standable` 且物品最少）；
产出仍留在中心。凡是有「输入格」和「输出格」的结构，两个位置必须分开定义。

### 22. `HaulToCell` 会预定**目标格**：WorkGiver 必须给每个人不同的落点

**日期**：2026-10-24（凝聚台送料实机刷红字）

**现象**：日志里成片：

```
Could not reserve (134, 0, 140) (layer: null) for Chili for job HaulToCell ...
Existing reservers: [0] Gypsy (job: HaulToCell ... B = (134, 0, 140), toil: 4, maxPawns: 1)
TryMakePreToilReservations() returned false for a non-queued job right after StartJob()
```

小人被派了活却站着不动，还刷 Warning。

**原因**：`JobDriver_HaulToCell.TryMakePreToilReservations` 会同时预定
**A=材料** 和 **B=存放格**，且 `maxPawns = 1`。我的 `FindDropCell` 对所有人都返回
「最空的那一格」，于是第二个搬运工一开工就预定失败。

**定性做法**：`WorkGiver.HasJobOnThing` / 落点规划里必须 `pawn.CanReserve(cell)`，
让每个小人挑**自己预定得到的**空位（多格建筑天然可以并行）。
只判 `CanReach` 是不够的——可达 ≠ 没被别人占。

### 23. 想换掉技能瞄准的准星，必须自定义 Verb 且**不调 `base.DrawHighlight`**

**日期**：2026-10-24（玩家嫌剑气瞄准的蓝色准星没用）

**现象**：点「泰拉剑气」后地上是个原版蓝色十字准星，玩家看不出射程，也看不出这一剑会扫到哪。

**原因**：准星是 `Verb_CastAbility`/`Targeter` 那条绘制链画的，`Ability.DrawHighlight`
**不可重写**（`CS0115`）。要换只能在 `verbProperties` 里写自己的 `verbClass`，
重写 `Verb.DrawHighlight(LocalTargetInfo)`。

**两个连带坑**：

1. **绝不能调 `base.DrawHighlight()`**：父类依赖 `ability` 状态，一抛异常整层 GUI 挂掉
   （表现为「点技能后所有 UI 消失」）。整段绘制还要包 try/catch + `Log.ErrorOnce`。
2. **引擎不会把 ability 挂到自定义 verb 上**：得在自己的 `Ability` 构造函数里补
   `if (verb is Verb_CastAbility cast && cast.ability != this) cast.ability = this;`，
   否则 `Verb_CastAbility.OnGUI` / `DrawAttachmentExtraLabel` 每帧 NRE。
