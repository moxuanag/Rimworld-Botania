# 方案：魔力网络重构 + 两朵防御花美术/射程修复

> 状态：**待用户确认细节后实施**（2026-11-24）
> 依据：`AGENTS.md`（框架式设计 / 先参考原版 / 先方案后实现）、现有 `CompManaStorage`、`CompManaRelay`、
> `ManaSourceUtil`、`ManaNetworkPreview`、`ManaDeviceCore`、`ManaProducerCore` 的实际代码。

---

## 一、现状诊断（为什么会「有两个范围」）

| 位置 | 现在的机制 | 玩家看到的效果 |
|---|---|---|
| 魔力池 `CompManaStorage` | 只存魔力；XML 挂 `CompProperties_RadiusRing` 画 **6 格**黄圈 | 玩家以为「6 格内才有效」 |
| 各设备（灯/修复器/通量场/明心莲/荆棘花/炮塔…） | 每个设备自己有 `searchRadius`（6 / 8 / 10 / 12 不等），自己就近找池子 | 12 格外的炮塔照样能吃到魔力 |
| 中继塔 `CompManaRelay` | 既是 `IManaSource`（有容量 6000、内部储魔、每 30 tick 从上游「拉」魔力、10% 损耗），又是网络节点 | 玩家把它当「电池」用，但它其实是个中继缓冲 |

**结论**：池子的圈（6）与设备各自的搜索半径（6~12）是两套互不相干的数值 —— 这就是「两个范围」的来源。

---

## 二、目标模型（用户描述）

一个**统一的网络覆盖**：

```
魔力池节点（半径 R池）  ─┐
                          ├─→ 覆盖圆并集 = 网络范围
中继塔节点（半径 R塔，已连接才有覆盖） ─┘

网络范围内：
  · 产魔花 → 把魔力送进网络
  · 功能花 / 消耗设备 → 直接从网络抽取魔力
  · 设备之间不再各自有搜索半径
中继塔：纯扩展建筑。范围内有一格属于「有魔力的网络」→ 视为已连接（并扩展覆盖）；
        否则提示「无可用魔力网络」。
```

### 2.1 连通判定（建议算法）

1. 所有**魔力池**是种子节点，永远「已连接」。
2. **中继塔**：存在任一已连接节点 N，使 `dist(塔, N) <= 塔.半径 + N.半径` → 该塔已连接。
3. 反复迭代到不再变化（支持链式：池 → 塔1 → 塔2 → 塔3）。
4. **网络覆盖** = 所有已连接节点的覆盖圆并集。
5. 设备（产魔/耗魔）判定：**设备所在格落在任一已连接节点的圆内**即属于该网络。

### 2.2 取 / 送魔力

- **送**（产魔花）：优先送进「能接收且距离最近」的已连接池；池满则跳下一个；全满则不产（与现在语义一致）。
- **取**（消耗设备）：从网络内所有池中按**距离由近到远**依次扣，直到凑够或遍历完。
- **共享问题**：见「待确认 ②」——同一网络内多个池是否视为一个大池。

### 2.3 框架落点（这是关键：只改一处，全部设备生效）

| 文件 | 改动 |
|---|---|
| **新增** `Source/Framework/ManaNetwork.cs` | `IManaNetworkNode`（半径 + 是否为池）、`ManaNetworkSystem`（节点登记/连通重建/覆盖查询/共享取送） |
| **新增** `Source/MapComponent_ManaNetwork.cs` | 宿主：缓存节点列表；建筑增删时打 dirty；每 250 tick 保底重建 |
| `Source/Framework/ManaDeviceCore.cs` | `FindSource()` 内部改为查网络（设备本身不再用自己的 searchRadius） |
| `Source/Framework/ManaProducerCore.cs` | `FindTarget()` 同样改为查网络 |
| `CompManaStorage` | 实现 `IManaNetworkNode`（提供 R池）；保留存魔、相邻池平衡 |
| `CompManaRelay` | **重写**：只保留 `radius` 与「已连接」状态；删除容量/储魔/拉取/损耗逻辑 |
| `ManaNetworkPreview` | 重写：选中池或塔时，画出**真实连通关系**（自己的覆盖圆 + 相连节点 + 未连接的塔标红） |
| `ManaSourceUtil` | 保留类名（其它代码还引用），内部改为「查网络」；旧的 `FindNearest(位置, 半径, ...)` 语义废弃 |

> 设备侧 XML 里的 `<searchRadius>` 将**全部移除**（改由网络决定），props 字段标 `[Obsolete]` 并在 `ConfigErrors` 里给出提醒，
> 避免以后有人以为它还有用。

## 三、数值建议（待确认）

| 项 | 建议值 | 理由 |
|---|---|---|
| 魔力池网络半径 | **10**（原显示环 6） | 比现在大一点，替代原来设备 6~12 的混合半径 |
| 简易魔力池 | **6** | 小池子服务范围也小，形成取舍 |
| 中继塔扩展半径 | **10** | 与池同量级，链式铺设才有意义 |
| 相邻池自动平衡 | 保留 | 与网络共享不冲突（平衡只影响相邻池之间的水位） |

## 四、兼容性与风险

| 风险 | 说明 | 对策 |
|---|---|---|
| **老存档中继塔里的魔力** | 塔不再储魔，存档里 `mana` 字段被忽略 → 塔里的魔力「消失」 | 读档时把旧塔的魔力**转入最近池**（一次性迁移），并在日志记一条 |
| 玩家布局失效 | 以前靠「塔当电池」的布局会变弱/变强 | 文档 + CHANGELOG 明确写「中继塔改为纯扩展，不再储魔」 |
| 数值膨胀 | 网络共享 = 一个满池能供整个网络，实际增强明显 | 池半径从 6 提高到 10 的同时，把设备侧原本 10~12 的搜索半径取消（净变化不大），必要时再调 |
| 性能 | 连通性重建是 O(n²)（n 一般 < 50） | 只在 dirty（建筑增删/读档）与每 250 tick 重建；查询直接遍历节点，无每 tick 全图扫描 |
| 平铺存档键 | 网络状态不入档（每次重建即可） | 不新增 Scribe 键，避免撞键 |
| DLC / 其它模组 | 全部自有组件，不 Patch 原版 | 无冲突 |

## 五、两朵防御花的美术重做（问题：底座与炮塔顶不协调）

**问题根因**（对照现有 4 张图）：

1. **中心不统一**：底座花体画在 (64,66) 附近，炮塔顶画在 (64,64)，旋转时轴心偏一点点就会「漂」。
2. **尺寸不统一**：底座直径约 100px，炮塔顶的炮管从 y=18 一直伸到 y=104，几乎和底座一样高；旋转时像是「另一张图叠上来」。
3. **描边与配色不统一**：底座品红花瓣 + 深绿描边，炮塔顶却是亮绿管 + 米色管口，色系断层。
4. **缺少「装在底座上」的过渡**：底座中心没有花托，顶部底部没有对应的托盘，接缝处直接硬接。

**重做规格（两朵花统一）**：

| 项 | 规格 |
|---|---|
| 尺寸 | 128×128，PNG |
| 中心 | 都精确画在 (64, 64)，底座与顶部同轴 |
| 顶部尺寸 | 直径 ≤ 76px（明显小于底座 100px），形成「装在花托上」的层次 |
| 描边 | 统一 2px 深色 `(30,26,34)` |
| 配色 | 共用一套：暗绿 `#305A3A` / 绿 `#549254` / 亮绿 `#7EBE76` / 品红 `#CC5498` / 暖白高光 |
| 过渡 | 底座中心画「花托」（直径 34px 的深色圆盘 + 一圈亮边），顶部底部画同直径的「托盘底」，两者重叠 2~3px 消缝 |
| 朝向 | 炮管一律朝**正北（上）**，管口高光在正上 |

**两套风格方向（请选一套）**：

- **方案 A「花萼托座」**：底座 = 低矮花萼 + 苔藓土台（视觉重心低、暗），顶部 = 完整花头（花瓣护罩包住炮管）+ 明暗对比强。旋转时像花冠在转。
- **方案 B「一体化花体」**：底座 = 花茎 + 环绕叶片，顶部 = 收拢的花苞形炮塔（炮管从花苞中心伸出）。整体更像一株植物而不是「花+炮」。

## 六、迫击炮射程与射程圈（上一版没达到设想）

**引擎限制（已实测）**：`GenDraw.DrawRadiusRing` 的预计算格子表上限是 `GenRadial.MaxRadialPatternRadius ≈ 79.8`。
超过就每帧报错且不画；自己用线段补画会被地形遮挡（需抬到 MetaOverlays，已修）。

**可选方案**：

| 方案 | 射程 | 环的表现 | 说明 |
|---|---|---|---|
| **1（推荐）** | **78** | 引擎原生白圈，完美 | 78 格已经是「跨半个基地」，且能完整显示 |
| 2 | 100 | 自绘线段环（现在是 128 段，可改成点阵/虚线） | 能显示，但和原版白圈观感有差异 |
| 3 | 100 | 只画内圈 10 + 面板文字写「射程 100」 | 最省事，但选中的圈不是射程圈 |

> 我的建议：**方案 1（78）**。理由：射程圈是玩家唯一能看到的范围反馈，为了 22 格多出来的射程牺牲「看得见」不值得；
> 而且 100 格在 1.5 倍地图下已经接近「半张图」，对防御建筑偏强。
